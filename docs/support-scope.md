# 当前支持范围

选择芯片或遇到“型号已排除”的报错时，先查看本页。支持型号由 `data/support-policy.json` 定义，下表型号目前不能通过框架构建或生成工程。

| 排除组 | 型号/配置数 | 原因 |
|---|---:|---|
| STM32G411、STM32G414 | 23 | 器件资料不足；CMSIS 芯片定义、DFP 器件支持包与 pin XML 引脚数据中的内存等规格存在冲突，尚未确认正确值 |
| STM32H7R3/R7、STM32H7S3/S7 | 20 | FDCAN 运行故障尚无经过验证的修复 |
| STM32H543、STM32H553 | 14 | RTC 保留状态、LSE 旁路及备份域复位问题未解决 |
| 合计 | 57 | 从项目生成、批量构建、公开芯片 feature 编译开关和支持范围验证中排除 |

完整 feature 名称及排除原因见 [support-policy.json](../data/support-policy.json)。芯片目录生成器按这份清单排除型号，使用完整名称逐项匹配。某个型号编译失败时仍会报错，不会自动把它从支持范围中移除。

项目当前支持 895 个型号、921 个芯片/内核配置，覆盖 F0/F1/F2/F3/F4/F7、G0/G4、H5/H7。双核 H7 的 M7/M4 分别计数。原始 ST 数据快照包含 952 个型号、978 个芯片/内核配置，仍保留用于核对资料来源。支持范围内有 28 个配置缺少上游实现，仓库为它们提供了对应准确型号的芯片代码，因此当前范围内缺少芯片实现的配置数为 0。

以下入口使用同一排除结果：

- `cargo xtask list-chips` 仅列出范围内配置。
- `cargo xtask new`、`build` 和 `peripherals --chip` 对已排除型号返回带原因的错误；不会创建工程或启动 MCU 构建。
- `matrix` 和 `peripherals` 先对范围内配置排序，再分成批次执行；范围内若有配置缺少芯片实现，会报错并保留问题。
- `App`、`embodied-stm32` 的公开 Cargo 芯片 feature 和 `data/generated/target-map.json` 不再包含已排除配置。
- `cargo xtask coverage` 的 `builds` / `core_builds` 统计 921 个范围内配置；`excluded_builds` 单列 57 项及原因，`catalogue_core_builds` 保留 978。原始目录统计和上游差集仍反映完整 ST 快照。
- CI（持续集成）的代表型号构建不包含 H543/H553、H7R/S，也不运行 H7R/S FDCAN 诊断作业；全型号构建使用同一范围。发布使用 H723。

`vendor` 和补丁中仍保留部分已排除器件的源码及历史验证记录，因为其他 H5/H7 器件也依赖其中的寄存器定义、驱动或补丁生成步骤。查看到这些源码时，仍应以上面的支持清单为准。直接依赖 `vendor/embassy-stm32`、绕开框架入口的项目不在支持范围内；已经生成的旧工程也不会自动更新。

为范围内芯片生成独立 App 时，使用 Rust 1.98.1 和完整、准确的 feature 名称。构建通过后仍需在实际板卡上验证。
